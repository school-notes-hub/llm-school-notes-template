# Complete an authorized note operation

This is a portable working method, not a scheduler or permission to change an agent runtime. Read it for a multi-page ingest, correction, subject refresh or media operation. The detailed teaching rules remain in the modules linked from [AGENTS.md](../AGENTS.md).

## Establish the task once

Preserve the user's requested result across status questions and clarifications. Record scope, owner, applicable authorizations (including an authorized commit/push), pages and existing paid request/job IDs in one small operation record. Reuse an existing maintenance/evidence record rather than making parallel planning registries. No per-page budget resets; older and new lessons may only share a budget when the user's authorization covers both. A page needing no new diagram is a valid explicit decision; a requested banner is still a deliverable.

Keep a compact checklist in the existing maintenance/evidence record for substantial operations. Do not add source texts, credentials, personal information or raw transcripts to operational state. A simple single-page change does not need a separate planning record.

Read relevant rules once, not after every tool call or delegate return. Batch independent file reads; use indexes and bounded reference/curriculum retrieval. A repeated rule read needs a reason: changed revision, lost context or a newly applicable task. Runtime setup is done once under [page-check setup](page-check.md) and the tool installation guides. Ordinary note maintenance must not install npm packages, create a scratch renderer or rewrite global skills merely to repeat a known check. Outside a school-notes run, if a required runtime is unavailable, report that specific blocker and continue independent content work; inside a run the tool builds and checks the pages, and a missing local renderer is not a blocker.

## Work by dependencies

1. Inventory pages, relevant sources, unresolved evidence and existing images. Identify a shared source or summary that can affect several pages. Give one agent ownership of each edited file; delegates return findings/artifacts or work on disjoint files, never competing writes to the same page.
2. Finalize a page's supported claims, learning scope, terminology and source attribution before its image prompt. Record source/page/asset hashes in the existing evidence. Do not wait for unrelated pages to finish before preparing an already stable page's image. When the environment supports it, independent content work can overlap a running image request.
3. Reuse the repository image/visual executors. Preserve the cumulative request and attempt ledger, its locks and unknown-outcome handling. Never bypass the paid executor lock or launch uncontrolled image batches for speed. Do not generate an infographic just to use an available tool.
4. Inspect the actual delivered image, embed the accepted artifact, and check its final page. Read/inspect unchanged evidence once and reuse it only while the relevant inputs, interpretation and scope remain unchanged. A changed upstream claim invalidates dependent images, summaries and quiz answers even if their files did not change.
5. In a school-notes run the tool builds and checks the pages (formulas included); run no renderer yourself. Outside a run, check the affected pages with an available prepared renderer; the optional repository page checker is one local diagnostic. Reuse unchanged render results; inspect changed pages and their affected diagrams in phone and desktop views. A successful renderer is not a factual, visual or learner acceptance verdict. Fix findings, rerun only affected checks and inspect the changed result.
6. Close the full authorized operation: coverage, source labels, precision/reading order, links, images, evidence index, log, diff and secret/privacy checks; then commit and, if authorized, push and verify the remote. Do not start a new renderer, broad extra review or optional redesign after these checks pass without a new concrete finding.

## Status is not completion

Answer an incoming question briefly, keep the original objective, and execute the next authorized step in the same active run. A progress message is intermediate. A text-only final answer may end the model loop in a chat harness; use its supported intermediate progress mechanism and continue real work. Do not assume that an unfinished task list or the phrase "I continue" restarts an idle invocation.

Distinguish **task state** from **execution state**. `active` in a saved record means unfinished authorized work; it does not prove a running process. Report "running" only with evidence of an active invocation/job. If stopped, say so and give the next step. When waiting on a running delegate, identify the real outstanding job; when its result arrives, integrate it and finish. A status question does not cancel the operation. A user stop/pause, a concrete external blocker or an actual execution limit does stop it; record the reason and do not silently restart against it.

A final completion message is allowed only after the requested result and delivery are verified. It names the result, checks, material limits and the actual commit/push outcome. It never substitutes an apology or intention for the unfinished work.

## Closure and handoff

Keep scope, completed items, pending work, existing paid request IDs and evidence links in the operation's existing maintenance/review record. A short Markdown checklist is enough; do not require a second JSON registry or duplicate the source and cost ledgers. Record an explicit no-change result when inspection finds nothing to update.

Before reporting completion, compare the requested scope with the final diff and evidence, check the actual commit and authorized remote delivery, and name any remaining blocker. A renderer receipt, a saved status word or a model's completion claim cannot prove scope coverage or publication. Never advance an independent reviewer's checkpoint on their behalf.

An unattended runner requires its own reviewed contract for input observation, successful processing, bounded retries, cancellation and publication. This policy does not implement such a runner or authorize an automatic restart. Runtime setup and any required adapter remain separate from ordinary note editing; project code is distributed through Git, not hidden runtime or global-skill patches.
